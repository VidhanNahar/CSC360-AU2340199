## Detailed Explanations

### 1. TriangleFX System Architecture

The core objective of **TriangleFX** is to deliver an end-to-end interactive desktop tool bridging linear algebra, computational geometry, and graphical user interfaces. Rather than tightly coupling UI components with geometric logic, the system is designed around a sequential processing pipeline.

```text
  ┌─────────────────────────────────────────────────────────────────────────┐
  │                         TriangleFX Data Pipeline                        │
  └─────────────────────────────────────────────────────────────────────────┘
        │
        ▼
   [ User Input ]           3 text strings (e.g., "x + y = 8", "y = 2x + 1")
        │
        ▼
   [ Equation Parser ]      Lexical scanning, regex matching, sign handling
        │
        ▼
   [ Canonical Models ]     3 Standardized Line objects: Ax + By = C
        │
        ▼
   [ Geometry Engine ]      Computes pairwise intersections (P₁₂, P₂₃, P₃₁)
        │
        ▼
   [ Shape Validator ]      Tests for non-degeneracy, collinearity & area > 0
        │
        ▼
   [ Presentation Layer ]   Plots scaled vertices on Canvas & updates status
```

#### Pipeline Responsibilities
* **Input Layer**: Captures raw text expressions from the user interface.
* **Parser Layer**: Sanitizes tokens, balances variables across the equality operator, and outputs canonical coefficients $(A, B, C)$.
* **Geometry Engine**: Solves three simultaneous pairwise line intersections using $2 \times 2$ determinants (Cramer's rule).
* **Validation Layer**: Confirms that three distinct points exist and their enclosed area exceeds a non-zero tolerance threshold ($\epsilon$).
* **Renderer & Feedback Layer**: Maps Cartesian coordinates to the JavaFX `Canvas` pixel grid, drawing lines, filled triangles, and vertex callouts.

### 2. Natural Equation Parsing and Normalization

In earlier iterations, coefficients were entered into individual matrix input cells. TriangleFX elevates user experience by allowing natural mathematical expressions.

```text
  Supported Inputs:
  ├── Standard Form:         2x - 3y = 10
  ├── Slope-Intercept:       y = 2x + 1  ──►  -2x + 1y = 1
  ├── Vertical Line:         x = 4       ──►   1x + 0y = 4
  └── Horizontal Line:       y = -5      ──►   0x + 1y = -5
```

#### Normalization Strategy

Any linear equation in two variables can be restructured to:

$$Ax + By = C$$

To parse this reliably without a heavyweight compiler framework, the parser follows a three-step lexical normalization:

1. **Splitting on Equality**: Divide the string into a Left-Hand Side (LHS) and a Right-Hand Side (RHS).
2. **Term Extraction**: Use regular expressions to extract terms containing $x$, terms containing $y$, and bare constants.
3. **Algebraic Transposition**: Move all variable terms to the LHS (reversing their signs if originally on the RHS) and all constant scalars to the RHS.

```java
import java.util.regex.Matcher;
import java.util.regex.Pattern;

public final class EquationParser {
    // Matches optional sign, optional decimal/integer coefficient, and variable name (x or y)
    private static final Pattern TERM_PATTERN = 
        Pattern.compile("([+-]?\\s*\\d*\\.?\\d*)\\s*([xy])", Pattern.CASE_INSENSITIVE);

    public record ParsedLine(double a, double b, double c) {}

    public static ParsedLine parse(String rawEquation) {
        if (rawEquation == null || !rawEquation.contains("=")) {
            throw new IllegalArgumentException("Equation must contain an '=' sign.");
        }

        String[] parts = rawEquation.split("=");
        if (parts.length != 2) {
            throw new IllegalArgumentException("Equation must have exactly one '=' operator.");
        }

        String lhs = parts[0].replaceAll("\\s+", "");
        String rhs = parts[1].replaceAll("\\s+", "");

        double a = extractCoefficient(lhs, "x") - extractCoefficient(rhs, "x");
        double b = extractCoefficient(lhs, "y") - extractCoefficient(rhs, "y");
        double c = extractConstant(rhs) - extractConstant(lhs);

        if (Math.abs(a) < 1e-9 && Math.abs(b) < 1e-9) {
            throw new IllegalArgumentException("Equation does not define a valid 2D line (both A and B are 0).");
        }

        return new ParsedLine(a, b, c);
    }

    private static double extractCoefficient(String side, String variable) {
        Matcher matcher = TERM_PATTERN.matcher(side);
        double total = 0.0;
        while (matcher.find()) {
            if (matcher.group(2).equalsIgnoreCase(variable)) {
                String coeffStr = matcher.group(1).replaceAll("\\s+", "");
                if (coeffStr.isEmpty() || coeffStr.equals("+")) total += 1.0;
                else if (coeffStr.equals("-")) total -= 1.0;
                else total += Double.parseDouble(coeffStr);
            }
        }
        return total;
    }

    private static double extractConstant(String side) {
        // Strips variable terms to isolate pure constants
        String withoutVars = side.replaceAll("([+-]?\\s*\\d*\\.?\\d*)\\s*[xyXY]", "");
        if (withoutVars.isEmpty() || withoutVars.equals("+")) return 0.0;
        return Double.parseDouble(withoutVars);
    }
}
```

### 3. Pairwise Intersections and Geometric Validation

Given three parsed lines $L_1, L_2, L_3$ in standard form:

$$L_1: A_1 x + B_1 y = C_1$$
$$L_2: A_2 x + B_2 y = C_2$$
$$L_3: A_3 x + B_3 y = C_3$$

The geometry engine computes three candidate intersection vertices:

$$P_{12} = L_1 \cap L_2, \quad P_{23} = L_2 \cap L_3, \quad P_{31} = L_3 \cap L_1$$

```text
                           L₁
                          /  \
                         /    \
                       P₁₂    P₃₁
                       /        \
             ─────────X──────────X───────── L₃
                     /            \
                    /              \
                  L₂                P₂₃
```

#### Degeneracy Screening Table

The validation engine systematically filters out non-triangle conditions:

| Geometric Condition | Algebraic Signature | Application Response |
| :--- | :--- | :--- |
| **Parallel Lines** | $D_{ij} = A_i B_j - A_j B_i \approx 0$ for any pair | Reject: At least two lines do not intersect. |
| **Coincident Lines** | $D = D_x = D_y \approx 0$ for any pair | Reject: Duplicate/overlapping lines specified. |
| **Concurrent Lines** | $P_{12} \approx P_{23} \approx P_{31}$ (Single intersection point) | Reject: All three lines meet at a single shared vertex. |
| **Collinear Points** | Shoelace Area $\le \epsilon$ | Reject: Points are collinear; zero area enclosed. |
| **Valid Triangle** | All $D_{ij} \neq 0$, points are distinct, and $\text{Area} > \epsilon$ | Accept: Proceed to Canvas rendering. |

### 4. JavaFX Canvas Rendering & Coordinate Transformation

A common challenge in computer graphics is reconciling **Cartesian coordinate space** (where $+y$ points upward) with **screen/canvas coordinate space** (where $(0,0)$ is the top-left pixel and $+y$ points downward).

```text
    MATHEMATICAL CARTESIAN SPACE                JAVAFX CANVAS SPACE (Pixels)
              +y                                (0,0) ──────────────► +x
               │                                  │
               │   • P(x, y)                      │       • P'(x', y')
               │                                  │
    ───────────┼───────────► +x                   │
               │                                  ▼
               │                                 +y
```

#### Viewport Auto-Scaling and Centering

To prevent the rendered triangle from appearing tiny, clipped, or off-screen, the application computes an axis-aligned bounding box (AABB) around the three vertices:

$$x_{\min} = \min(x_1, x_2, x_3), \quad x_{\max} = \max(x_1, x_2, x_3)$$
$$y_{\min} = \min(y_1, y_2, y_3), \quad y_{\max} = \max(y_1, y_2, y_3)$$

Let the canvas have dimensions $W \times H$ with an inner margin/padding $M$. The dynamic scaling factor $S$ and pixel offsets are calculated as:

$$S = \min\left( \frac{W - 2M}{x_{\max} - x_{\min}}, \frac{H - 2M}{y_{\max} - y_{\min}} \right)$$

For any Cartesian point $(x, y)$, its corresponding canvas pixel coordinate $(x', y')$ is:

$$x' = M + (x - x_{\min}) \cdot S$$
$$y' = H - \left( M + (y - y_{\min}) \cdot S \right)$$

Notice the inversion in $y'$, which correctly restores the intuitive mathematical orientation on the display.

## Discussion

1. **User Experience vs. Parser Complexity**:
   * Requiring users to enter pre-isolated coefficients ($A, B, C$) minimizes parsing errors but imposes cognitive friction. Supporting freeform text equations significantly enhances usability but demands robust regular expression matching and defensive syntax validation.
2. **Viewport Fitting and Extreme Aspect Ratios**:
   * Triangles with one extremely long side and a tiny angle (needle-like triangles) can cause one dimension of the bounding box to dominate, compressing the visual output. Applying a minimum scale threshold and aspect-ratio clamping ensures the rendered shape remains visually legible.
3. **Engineering Integrity in Documentation**:
   * A critical lesson from this planning milestone is the importance of maintaining an accurate project `README.md`. A repository that claims a system is "functional" when it only contains documentation harms credibility. Clearly separating **completed baselines** from **planned phases** creates transparency and trust among collaborators.

## Key Takeaways

* **Decoupled Architecture**: TriangleFX establishes clear separation between text parsing, geometric computation, shape validation, and canvas rendering.
* **Equation Flexibility**: Supporting freeform equations ($Ax + By = C$, $y = mx + c$, $x = k$) provides an intuitive user interface while maintaining a single internal canonical representation.
* **Strict Degeneracy Screening**: Verifying a valid triangle requires screening for parallel lines ($D = 0$), coincident lines, concurrent intersection points, and non-zero Shoelace area ($|D| > \epsilon$).
* **Screen Coordinate Inversion**: Transforming Cartesian space to JavaFX Canvas coordinates requires inverting the vertical axis ($y' = H - y_{\text{scaled}}$) and applying dynamic bounding-box auto-scaling.
* **Structured Development Discipline**: Following an eight-phase implementation plan combined with branch/PR Git workflows ensures steady, verifiable, and team-aligned progress.
