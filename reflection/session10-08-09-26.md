## Detailed Explanations

### 1. Reflection in Java

**Reflection** is an advanced feature in Java that allows an executing program to introspect (examine) and manipulate its own internal structure, classes, interfaces, fields, and methods at runtime, without knowing their names at compile time.

```text
  Source Code (.java) ──► Compiler (javac) ──► Bytecode (.class)
                                                     │
                                                     ▼
                                            JVM ClassLoader
                                                     │
                                                     ▼
                                            java.lang.Class<?>
                                      (Runtime Metadata Descriptor)
                                     ┌──────────────┬──────────────┐
                                     │ Constructors │    Fields    │
                                     │   Methods    │  Annotations │
                                     └──────────────┴──────────────┘
                                                     │
                                   Reflection API (java.lang.reflect)
                                   • Dynamic object creation
                                   • Dynamic method invocation
                                   • Access private fields/methods
```

#### Core Capabilities of Reflection
* **Introspection**: Discovering the class hierarchy, interfaces, constructors, methods, and fields of an unknown object at runtime.
* **Dynamic Instantiation**: Constructing instances of classes dynamically using `Class.forName()` and `Constructor.newInstance()`.
* **Dynamic Invocation**: Calling methods dynamically by name using `Method.invoke()`.
* **Encapsulation Bypass**: Inspecting or mutating `private` fields and methods by invoking `AccessibleObject.setAccessible(true)` (subject to JVM SecurityManager / Module System constraints).

#### Reflection in Practice

```java
import java.lang.reflect.Constructor;
import java.lang.reflect.Field;
import java.lang.reflect.Method;

public class ReflectionDemo {
    public static void main(String[] args) {
        try {
            // 1. Dynamic Class Loading
            Class<?> clazz = Class.forName("java.util.ArrayList");
            System.out.println("Loaded Class: " + clazz.getName());

            // 2. Dynamic Object Instantiation via default constructor
            Constructor<?> constructor = clazz.getDeclaredConstructor();
            Object listInstance = constructor.newInstance();
            System.out.println("Instantiated: " + listInstance.getClass().getSimpleName());

            // 3. Dynamic Method Lookup and Invocation
            Method addMethod = clazz.getMethod("add", Object.class);
            addMethod.invoke(listInstance, "Java Reflection");
            addMethod.invoke(listInstance, "Dynamic Invocation");

            Method sizeMethod = clazz.getMethod("size");
            Object size = sizeMethod.invoke(listInstance);
            System.out.println("ArrayList size via reflection: " + size);

            // 4. Introspecting Declared Methods
            System.out.println("\nSample Declared Methods:");
            Method[] methods = clazz.getDeclaredMethods();
            for (int i = 0; i < Math.min(5, methods.length); i++) {
                System.out.println(" - " + methods[i].getName() + "()");
            }

        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}
```

#### Trade-offs & Practical Considerations
* **Performance Overhead**: Reflection involves dynamic type resolution, preventing certain JIT compiler optimizations. Reflective operations are substantially slower than direct method calls.
* **Security & Encapsulation**: Reflective access can violate encapsulation boundaries by inspecting private state. Modern Java modules (Java 9+) restrict reflective access across module boundaries unless explicitly opened (`opens`).
* **Loss of Compile-time Safety**: Errors in class or method names produce runtime exceptions (`ClassNotFoundException`, `NoSuchMethodException`) instead of compile-time compiler errors.

### 2. Exceptions, Assertions, and Logging

Robust Java applications require disciplined error handling, internal invariant checking during development, and persistent diagnostic observability.

#### The `Throwable` Class Hierarchy

All runtime errors and exceptions stem from `java.lang.Throwable`.

```text
                             java.lang.Throwable
                               ┌──────┴──────┐
                               │             │
                       java.lang.Error   java.lang.Exception
                       (Fatal/System)        ┌──────┴─────────────────────┐
                       - OutOfMemoryError    │                            │
                       - StackOverflowError Checked Exceptions    RuntimeException
                                            (Compile-time enforced) (Unchecked / Logic)
                                            - IOException           - NullPointerException
                                            - SQLException          - ArithmeticException
                                            - ClassNotFoundException- ArrayIndexOutOfBoundsException
```

| Category | Enforced by Compiler? | Root Class | Typical Causes & Best Practices |
| :--- | :---: | :--- | :--- |
| **Checked Exceptions** | Yes (`try-catch` or `throws`) | `Exception` (excluding `RuntimeException`) | External, recoverable conditions (e.g., missing file, network drop, database down). |
| **Unchecked Exceptions** | No | `RuntimeException` | Program bugs, logic flaws, illegal arguments (e.g., `null` dereference, division by zero). |
| **Errors** | No | `Error` | Fatal system or JVM failures that programs typically cannot recover from (e.g., memory exhaustion). |

#### Assertions in Java

Assertions are boolean expressions that a developer believes will be true at a specific point in the program. They serve as internal sanity checks during development and testing.

* **Syntax**: `assert condition;` or `assert condition : "Descriptive failure message";`
* **JVM Execution State**: **Assertions are disabled by default** in Java to prevent any runtime performance penalty in production.
  * Enable assertions: `java -ea MainClass` (or `-enableassertions`)
  * Disable assertions: `java -da MainClass` (or `-disableassertions`)
  * Enable for a package: `java -ea:com.example... MainClass`

> [!WARNING]
> Assertions should never be used to validate public method arguments, because disabling assertions would silently skip validation. Use explicit `IllegalArgumentException` or `Objects.requireNonNull()` checks instead.

```java
public class AssertionDemo {
    public static void processOrder(int quantity, double price) {
        // Public API validation: Always enforced
        if (quantity <= 0 || price < 0.0) {
            throw new IllegalArgumentException("Invalid order arguments");
        }

        double total = quantity * price;

        // Internal assertion: Invariant check during development
        assert total >= 0.0 : "Computed order total cannot be negative: " + total;

        System.out.println("Order processed: $" + total);
    }
}
```

#### Diagnostic Logging with `java.util.logging`

Logging provides a production-safe way to track execution flow, warnings, and errors into files or consoles without relying on `System.out.println()`.

```text
  Application Code ──► Logger ──► Handler (Console / File) ──► Formatter ──► Output Stream
```

* **Standard Log Levels (Highest to Lowest)**:
  `SEVERE` $\to$ `WARNING` $\to$ `INFO` $\to$ `CONFIG` $\to$ `FINE` $\to$ `FINER` $\to$ `FINEST` (along with `ALL` and `OFF`).

```java
import java.util.logging.Level;
import java.util.logging.Logger;

public class LoggingDemo {
    // Unique logger per class
    private static final Logger logger = Logger.getLogger(LoggingDemo.class.getName());

    public static void main(String[] args) {
        logger.info("Application starting up...");

        try {
            int result = divide(10, 0);
            logger.fine("Calculation result: " + result);
        } catch (ArithmeticException ex) {
            logger.log(Level.SEVERE, "Failed to perform mathematical division", ex);
        }

        logger.warning("Configuration file missing; fallback defaults applied.");
    }

    private static int divide(int a, int b) {
        return a / b;
    }
}
```

### 3. Generic Programming

**Generics** (introduced in Java 5) allow types (classes and interfaces) to be parameters when defining classes, interfaces, and methods. Generics provide **compile-time type safety** and remove the necessity of explicit type casting.

```text
  Without Generics (Legacy / Raw Types):
    List list = new ArrayList();
    list.add("Hello");
    list.add(Integer.valueOf(42));     // Allowed by compiler!
    String s = (String) list.get(1);   // Crashes at RUNTIME: ClassCastException

  With Generics (Type-Safe):
    List<String> list = new ArrayList<>();
    list.add("Hello");
    list.add(42);                      // COMPILE-TIME ERROR: Incompatible types!
```

#### Core Components of Generics

1. **Generic Types & Type Parameters**: Using placeholders like `T` (Type), `E` (Element), `K` (Key), `V` (Value).
2. **Bounded Type Parameters**: Restricting allowed types with `T extends SuperClass & Interface`.
3. **Wildcards (`?`)**:
   * **Unbounded Wildcard (`<?>`)**: Accepts any type when only `Object` operations are needed.
   * **Upper-Bounded Wildcard (`<? extends T>`)**: Accepts `T` or any subclass of `T` (**Covariance**). Ideal for read-only producers.
   * **Lower-Bounded Wildcard (`<? super T>`)**: Accepts `T` or any superclass of `T` (**Contravariance**). Ideal for write-only consumers.
   * **The PECS Rule**: **P**roducer **E**xtends, **C**onsumer **S**uper.

```java
import java.util.ArrayList;
import java.util.List;

public class GenericsDemo {

    // Generic Method with Bounded Type Parameter
    public static <T extends Number> double sumNumbers(List<T> numbers) {
        double sum = 0.0;
        for (T num : numbers) {
            sum += num.doubleValue();
        }
        return sum;
    }

    // Producer Extends: Reading elements safely from source
    public static void printNumbers(List<? extends Number> list) {
        for (Number n : list) {
            System.out.println("Item: " + n);
        }
        // list.add(10); // COMPILE ERROR: Cannot write into ? extends Number
    }

    // Consumer Super: Writing elements safely into destination
    public static void addIntegers(List<? super Integer> list) {
        list.add(100);
        list.add(200);
    }

    public static void main(String[] args) {
        List<Integer> intList = new ArrayList<>();
        addIntegers(intList);
        System.out.println("Sum: " + sumNumbers(intList));
        printNumbers(intList);
    }
}
```

#### Type Erasure

Java implements generics via **type erasure**:
* The Java compiler checks types during compilation and inserts necessary implicit casts.
* The compiler then **erases** all generic type parameter information from the generated bytecode (replacing `T` with its bound, e.g., `Object` or `Number`).
* **Consequence**: At runtime, `List<String>` and `List<Integer>` both have the identical raw class `ArrayList.class`. Generic type parameters do not exist in runtime JVM bytecode, preserving backward compatibility with pre-Java 5 libraries.

### 4. Java Collections Framework

The **Java Collections Framework (JCF)** provides a unified architecture for storing, organizing, and manipulating groups of objects.

```text
                             java.lang.Iterable<E>
                                      │
                         java.util.Collection<E>
             ┌────────────────────────┼────────────────────────┐
             ▼                        ▼                        ▼
       java.util.List<E>        java.util.Set<E>        java.util.Queue<E>
     (Ordered, duplicates)     (Unique elements)        (Processing order)
       ├── ArrayList            ├── HashSet              ├── PriorityQueue
       └── LinkedList           ├── LinkedHashSet        └── ArrayDeque
                                └── TreeSet (SortedSet)

                         java.util.Map<K, V>
                       (Key-Value mappings, unique keys)
                         ├── HashMap
                         ├── LinkedHashMap
                         └── TreeMap (SortedMap)
```

#### Core Collection Interfaces & Implementations

| Interface | Concrete Class | Backing Data Structure | Ordering Guarantee | Duplicates? | Access / Search | Insertion / Deletion |
| :--- | :--- | :--- | :--- | :---: | :---: | :---: |
| **`List`** | `ArrayList` | Resizable Dynamic Array | Insertion order | Yes | $O(1)$ by index | $O(n)$ arbitrary ($O(1)$ amortized append) |
| **`List`** | `LinkedList` | Doubly-Linked List | Insertion order | Yes | $O(n)$ by index | $O(1)$ if node pointer known |
| **`Set`** | `HashSet` | Hash Table (`HashMap`) | None (arbitrary) | No | $O(1)$ lookup | $O(1)$ amortized |
| **`Set`** | `TreeSet` | Red-Black Balanced BST | Natural / `Comparator` | No | $O(\log n)$ | $O(\log n)$ |
| **`Map`** | `HashMap` | Hash Table + Bins | None | Unique Keys | $O(1)$ key lookup | $O(1)$ amortized |
| **`Map`** | `TreeMap` | Red-Black Balanced BST | Key sorted order | Unique Keys | $O(\log n)$ | $O(\log n)$ |

#### Collections Implementation Example

```java
import java.util.*;

public class CollectionsDemo {
    public static void main(String[] args) {
        // 1. List: Ordered collection with indexed access
        List<String> list = new ArrayList<>();
        list.add("Alpha");
        list.add("Beta");
        list.add("Alpha"); // Duplicates permitted
        System.out.println("ArrayList: " + list + " (Index 1: " + list.get(1) + ")");

        // 2. Set: Unordered collection enforcing uniqueness
        Set<String> set = new HashSet<>(list);
        System.out.println("HashSet (duplicates stripped): " + set);

        // 3. Map: Associative key-value dictionary
        Map<String, Integer> scoreMap = new HashMap<>();
        scoreMap.put("Alice", 95);
        scoreMap.put("Bob", 88);
        scoreMap.put("Charlie", 92);

        System.out.println("Scores Map:");
        for (Map.Entry<String, Integer> entry : scoreMap.entrySet()) {
            System.out.println(" - " + entry.getKey() + ": " + entry.getValue());
        }
    }
}
```

### 5. Views and Wrappers in Collections

In Java, a **view** is a specialized collection object that does **not** copy or duplicate data elements. Instead, it provides a restricted, alternate, or transformed window backed directly by an underlying collection.

```text
  Backing List:  [ "A", "B", "C", "D", "E" ]
                         ▲             ▲
                         │  subList    │
                         │   (1, 4)    │
  View Reference:        [ "B", "C", "D" ]
  
  * Mutating through the view alters the underlying backing list!
  * Structural mutations on the backing list will invalidate the sublist view (ConcurrentModificationException).
```

#### Major View and Wrapper Categories

1. **Subrange Views**:
   * `list.subList(fromIndex, toIndex)`: Provides an index window $[fromIndex, toIndex)$ into a list. Modifying the sublist mutates the backing list.
   * `sortedSet.subSet(from, to)`, `sortedSet.headSet(to)`, `sortedSet.tailSet(from)`.
2. **Collection View Adapters**:
   * `Arrays.asList(T... a)`: Produces a fixed-size `List` view backed by an array. Mutating an element via `list.set(i, val)` updates the array directly, but attempting `add()` or `remove()` throws `UnsupportedOperationException`.
   * `Map` collection views: `map.keySet()`, `map.values()`, and `map.entrySet()`.
3. **Unmodifiable Wrappers**:
   * `Collections.unmodifiableList(list)`, `Collections.unmodifiableSet(set)`, `Collections.unmodifiableMap(map)`.
   * Throws `UnsupportedOperationException` on mutating calls (`add`, `remove`, `set`).
   * *Note*: If the backing list is modified elsewhere, the unmodifiable view reflects those changes.
4. **Synchronized Wrappers**:
   * `Collections.synchronizedList(new ArrayList<>())`, `Collections.synchronizedMap(new HashMap<>())`.
   * Thread-safe wrappers where each individual method call is synchronized on a shared mutex monitor lock.

```java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.Collections;
import java.util.List;

public class ViewsAndWrappersDemo {
    public static void main(String[] args) {
        // 1. Array-backed List View
        String[] colors = {"Red", "Green", "Blue"};
        List<String> colorView = Arrays.asList(colors);
        colorView.set(0, "Crimson"); // Mutates backing array directly
        System.out.println("Updated array element: " + colors[0]); // "Crimson"

        // 2. SubList Range View
        List<Integer> numbers = new ArrayList<>(List.of(10, 20, 30, 40, 50));
        List<Integer> sub = numbers.subList(1, 4); // [20, 30, 40]
        sub.set(0, 999);
        System.out.println("Backing list after sublist update: " + numbers); // [10, 999, 30, 40, 50]

        // 3. Unmodifiable Wrapper
        List<Integer> readOnlyList = Collections.unmodifiableList(numbers);
        System.out.println("Read-only list access: " + readOnlyList.get(0));
        try {
            readOnlyList.add(100); // Throws UnsupportedOperationException
        } catch (UnsupportedOperationException e) {
            System.out.println("Caught expected exception: Modification denied on unmodifiable wrapper.");
        }
    }
}
```

### 6. Event Handling Architecture: Event Hierarchy, Sources, and Listeners

Java GUI systems (AWT, Swing) use the **Delegation Event Model** (an implementation of the **Observer Design Pattern**) to handle asynchronous user interactions like keystrokes and mouse clicks.

```text
  ┌─────────────────────────┐                        ┌─────────────────────────┐
  │      Event Source       │                        │     Event Listener      │
  │     (e.g., JButton)     │                        │  (e.g., ActionListener) │
  └────────────┬────────────┘                        └────────────┬────────────┘
               │                                                  │
               │         1. Registers via addActionListener(...)  │
               │◄─────────────────────────────────────────────────┘
               │
    [ User clicks button ]
               │
               │ 2. Constructs ActionEvent
               │ 3. Fires actionPerformed(ActionEvent e)
               │─────────────────────────────────────────────────►
```

#### The Delegation Architecture Roles

1. **Event Source**: The user-interface component (e.g., `JButton`, `JTextField`, `JCheckBox`) that detects physical inputs and generates an event object. It maintains a registry of interested listener objects.
2. **Event Object**: An instance encapsulating the context of what happened (source component, timestamp, coordinates, action command).
3. **Event Listener**: An interface defining one or more callback methods. When an event fires, the source iterates through its registered listeners and executes their callback methods.

#### AWT / Swing Event Class Hierarchy

```text
                       java.util.EventObject
                                 │
                        java.awt.AWTEvent
        ┌────────────────────────┼────────────────────────┐
        ▼                        ▼                        ▼
  java.awt.event.ActionEvent  AdjustmentEvent       ComponentEvent
  (Buttons, Menus, Enter)                           ┌─────┴─────┐
                                                    ▼           ▼
                                                FocusEvent  InputEvent
                                                           ┌────┴────┐
                                                           ▼         ▼
                                                       KeyEvent  MouseEvent
```

#### Event Handling Implementation in Swing

```java
import javax.swing.JButton;
import javax.swing.JFrame;
import javax.swing.JLabel;
import javax.swing.JPanel;
import java.awt.FlowLayout;
import java.awt.event.ActionEvent;
import java.awt.event.ActionListener;

public class EventHandlingDemo {
    public static void main(String[] args) {
        JFrame frame = new JFrame("Event Delegation Demo");
        frame.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
        frame.setSize(350, 150);

        JPanel panel = new JPanel(new FlowLayout());
        JLabel label = new JLabel("Click a button");
        JButton button1 = new JButton("Traditional Listener");
        JButton button2 = new JButton("Lambda Listener");

        // 1. Traditional Anonymous Inner Class Approach
        button1.addActionListener(new ActionListener() {
            @Override
            public void actionPerformed(ActionEvent e) {
                label.setText("Button 1 clicked at: " + e.getWhen());
            }
        });

        // 2. Modern Lambda Expression Approach (SAM - Single Abstract Method)
        button2.addActionListener(e -> label.setText("Button 2 clicked via Lambda!"));

        panel.add(button1);
        panel.add(button2);
        panel.add(label);

        frame.add(panel);
        frame.setVisible(true);
    }
}
```

### 7. Dialog Boxes in Graphical Interfaces

A **Dialog Box** is a secondary top-level window designed to display brief information, alert users to errors, prompt for confirmation, or gather user input.

```text
                  ┌─────────────────────────────────────┐
                  │       Main Application Window       │
                  └──────────────────┬──────────────────┘
                                     │
                             Presents Dialog
                                     ▼
                  ┌─────────────────────────────────────┐
                  │          Dialog Box Window          │
                  │   [ ! ] Save changes before exit?   │
                  │        [ Save ]   [ Cancel ]        │
                  └─────────────────────────────────────┘
```

#### Modal vs. Modeless Dialogs

| Property | Modal Dialog (`setModal(true)`) | Modeless Dialog (`setModal(false)`) |
| :--- | :--- | :--- |
| **Input Blocking** | Blocks all user interaction with parent/sibling windows until dismissed. | Allows user interaction across multiple application windows simultaneously. |
| **Execution Flow** | Typically blocks the calling thread (or event dispatch loop) until user closes it. | Returns immediately; code execution continues asynchronously. |
| **Common Use Cases** | File overwrite warnings, credentials login, critical error popups, file save confirmations. | "Find and Replace" tool windows, floating utility toolbars, non-blocking logs. |

#### Standard Dialogs with `JOptionPane`

`JOptionPane` provides static utility methods for standard dialog layouts:

* **Message Dialog**: `JOptionPane.showMessageDialog(parent, "Task finished!", "Info", JOptionPane.INFORMATION_MESSAGE)`
* **Confirmation Dialog**: `int choice = JOptionPane.showConfirmDialog(parent, "Delete record?", "Confirm", JOptionPane.YES_NO_OPTION)`
* **Input Dialog**: `String input = JOptionPane.showInputDialog(parent, "Enter your username:")`
* **Option Dialog**: Custom button choices and icons.

#### Custom Modal Dialogs with `JDialog`

When standard dialogs are insufficient, developers subclass or instantiate `JDialog` with custom layouts:

```java
import javax.swing.*;
import java.awt.*;

public class DialogDemo {
    public static void main(String[] args) {
        SwingUtilities.invokeLater(() -> {
            JFrame frame = new JFrame("Main Application");
            frame.setSize(400, 200);
            frame.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);

            JButton promptBtn = new JButton("Show Options");
            promptBtn.addActionListener(e -> {
                // 1. Standard JOptionPane Confirmation
                int result = JOptionPane.showConfirmDialog(
                    frame,
                    "Do you want to launch the custom modal dialog?",
                    "Confirmation",
                    JOptionPane.YES_NO_OPTION
                );

                if (result == JOptionPane.YES_OPTION) {
                    // 2. Custom Modal JDialog
                    showCustomDialog(frame);
                }
            });

            frame.setLayout(new FlowLayout());
            frame.add(promptBtn);
            frame.setVisible(true);
        });
    }

    private static void showCustomDialog(JFrame parent) {
        // Third parameter 'true' configures modal behavior
        JDialog dialog = new JDialog(parent, "Custom Configuration", true);
        dialog.setLayout(new BorderLayout(10, 10));
        dialog.setSize(280, 140);
        dialog.setLocationRelativeTo(parent);

        JLabel label = new JLabel("Enter setting value:", SwingConstants.CENTER);
        JTextField textField = new JTextField(15);
        JButton closeBtn = new JButton("Submit & Close");

        closeBtn.addActionListener(e -> {
            System.out.println("Submitted: " + textField.getText());
            dialog.dispose(); // Closes dialog and unblocks parent
        });

        JPanel centerPanel = new JPanel();
        centerPanel.add(textField);

        dialog.add(label, BorderLayout.NORTH);
        dialog.add(centerPanel, BorderLayout.CENTER);
        dialog.add(closeBtn, BorderLayout.SOUTH);

        dialog.setVisible(true); // Blocks until dismissed because modal is true
    }
}
```

## Key Takeaways

* **Reflection**: Enables dynamic class inspection and runtime invocation, driving frameworks like Spring and JUnit, but incurs performance overhead and bypasses compile-time type checking.
* **Exception Strategy**: Checked exceptions demand explicit handling for recoverable conditions, unchecked runtime exceptions indicate logic flaws, and `Error` represents critical JVM failures.
* **Assertions & Logging**: Assertions (`-ea`) verify internal invariants during development, while `java.util.logging` provides structured, configurable diagnostics for production runtime.
* **Generic Type Safety**: Generics prevent `ClassCastException` via compile-time verification; the PECS guideline (`extends` for reading, `super` for writing) dictates wildcard parameters, and type erasure strips types in bytecode.
* **Collections Trade-offs**: Selecting between `ArrayList`, `LinkedList`, `HashSet`, and `HashMap` depends on indexed access frequency, sorting needs, duplicate handling, and asymptotic time complexity requirements.
* **Views vs. Copies**: Sublists, array adapters (`Arrays.asList`), and collection wrappers are views backed directly by original collections—mutations reflect mutually across views.
* **Event Delegation Model**: Decouples UI event sources from event handlers using listener interfaces and observer callbacks, cleanly expressed with lambdas.
* **Dialog Architecture**: Modal dialogs halt interaction with the parent window until resolved for critical workflows, whereas modeless dialogs permit concurrent multi-window operations.
