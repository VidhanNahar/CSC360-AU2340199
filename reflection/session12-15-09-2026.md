## Detailed Explanations

### 1. Collinearity and Triangle Validation

In computational geometry, determining whether three arbitrary points $P_1(x_1, y_1)$, $P_2(x_2, y_2)$, and $P_3(x_3, y_3)$ form a genuine triangle requires confirming that they do not lie along a common straight line. Three collinear points span zero geometric area and fail to form a polygon.

```text
    VALID TRIANGLE (Non-Collinear)              DEGENERATE TRIANGLE (Collinear)
                 P₂                                  P₁ ─────── P₂ ─────── P₃
                /  \
               /    \                                     Area = 0
              /      \                                    (D = 0)
            P₁ ────── P₃
             Area > 0 (D ≠ 0)
```

#### The Signed Area (Shoelace Determinant)

Rather than computing edge lengths with square roots (which introduces floating-point error and runtime overhead via Heron's formula), the standard algebraic approach calculates the signed determinant of the vertex coordinates:

$$D = \begin{vmatrix} x_1 & y_1 & 1 \\ x_2 & y_2 & 1 \\ x_3 & y_3 & 1 \end{vmatrix} = x_1(y_2 - y_3) + x_2(y_3 - y_1) + x_3(y_1 - y_2)$$

The geometric area of the enclosed region corresponds to:

$$\text{Area} = \frac{1}{2} |D|$$

#### Vertex Orientation and Degeneracy

The algebraic sign of $D$ reveals the winding order of the vertices in 2D space:
* **$D > 0$**: The vertices follow a **counterclockwise (CCW)** traversal.
* **$D < 0$**: The vertices follow a **clockwise (CW)** traversal.
* **$D = 0$**: The points are **strictly collinear** (or contain duplicate coordinates), resulting in zero area.

#### Robust Java Implementation with Epsilon Comparison

Direct equality checks (`area == 0.0`) are unsafe with IEEE 754 floating-point numbers due to rounding inaccuracies during arithmetic operations. A threshold parameter ($\epsilon = 10^{-9}$) must be used instead:

```java
public record Point(double x, double y) {}

public final class GeometryUtils {
    private static final double EPSILON = 1e-9;

    public static double computeTwiceSignedArea(Point p1, Point p2, Point p3) {
        return p1.x() * (p2.y() - p3.y())
             + p2.x() * (p3.y() - p1.y())
             + p3.x() * (p1.y() - p2.y());
    }

    public static boolean isValidTriangle(Point p1, Point p2, Point p3) {
        double signedArea2 = computeTwiceSignedArea(p1, p2, p3);
        // Collinear or identical points yield |2 * Area| <= EPSILON
        return Math.abs(signedArea2) > EPSILON;
    }
}
```

### 2. Solving Line Intersections via Determinants and Cramer's Rule

When working with lines in coordinate space, the **standard general form** ($ax + by = c$) is far superior to the slope-intercept form ($y = mx + c$) because it represents vertical lines ($b = 0, a \neq 0$) without triggering division-by-zero exceptions.

```text
  Line 1:  a₁x + b₁y = c₁
  Line 2:  a₂x + b₂y = c₂

  ┌─────────────────────────────────────────────────────────────┐
  │                 Calculate Determinant (D)                   │
  │                     D = a₁b₂ - a₂b₁                         │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
            [ D ≠ 0 ]                        [ D ≈ 0 ]
        Unique Intersection             Lines are Parallel
        x = (c₁b₂ - c₂b₁) / D                    │
        y = (a₁c₂ - a₂c₁) / D      ┌─────────────┴─────────────┐
                                   ▼                           ▼
                           [ D_x ≈ 0 and D_y ≈ 0 ]     [ D_x ≠ 0 or D_y ≠ 0 ]
                              Coincident Lines             Distinct Parallel
                            (Infinite Solutions)             (No Solution)
```

#### Matrix Formulation

Two lines form a linear system:

$$\begin{bmatrix} a_1 & b_1 \\ a_2 & b_2 \end{bmatrix} \begin{bmatrix} x \\ y \end{bmatrix} = \begin{bmatrix} c_1 \\ c_2 \end{bmatrix}$$

Using Cramer's Rule, the primary and auxiliary determinants are:

$$D = a_1 b_2 - a_2 b_1$$
$$D_x = c_1 b_2 - c_2 b_1, \quad D_y = a_1 c_2 - a_2 c_1$$

#### Classification of Geometric Configurations

| Condition | Geometric Interpretation | Algebraic State |
| :--- | :--- | :--- |
| $|D| > \epsilon$ | **Single Intersection Point**: The two lines cross at exactly $(x, y) = (D_x / D, D_y / D)$. | Consistent and Independent |
| $|D| \le \epsilon$ and $(|D_x| > \epsilon \text{ or } |D_y| > \epsilon)$ | **Strictly Parallel**: The lines have identical slopes but different offsets; they never meet. | Inconsistent (No solution) |
| $|D| \le \epsilon$ and $|D_x| \le \epsilon$ and $|D_y| \le \epsilon$ | **Coincident**: Both equations define the exact same line; infinitely many points satisfy both. | Consistent and Dependent |

#### Implementation Model

```java
public record Line(double a, double b, double c) {
    public Line {
        if (Math.abs(a) < 1e-9 && Math.abs(b) < 1e-9) {
            throw new IllegalArgumentException("Coefficients 'a' and 'b' cannot both be zero.");
        }
    }
}

public sealed interface IntersectionResult {
    record SinglePoint(Point point) implements IntersectionResult {}
    record Parallel() implements IntersectionResult {}
    record Coincident() implements IntersectionResult {}
}

public static IntersectionResult findIntersection(Line l1, Line l2) {
    double d  = l1.a() * l2.b() - l2.a() * l1.b();
    double dx = l1.c() * l2.b() - l2.c() * l1.b();
    double dy = l1.a() * l2.c() - l2.a() * l1.c();

    double eps = 1e-9;
    if (Math.abs(d) > eps) {
        return new IntersectionResult.SinglePoint(new Point(dx / d, dy / d));
    } else if (Math.abs(dx) <= eps && Math.abs(dy) <= eps) {
        return new IntersectionResult.Coincident();
    } else {
        return new IntersectionResult.Parallel();
    }
}
```

### 3. Representing Three Lines as an Overdetermined System ($Ax = b$)

When extending the system to three simultaneous line equations:

$$a_1 x + b_1 y = c_1$$
$$a_2 x + b_2 y = c_2$$
$$a_3 x + b_3 y = c_3$$

We obtain an **overdetermined matrix system** having three constraints for only two unknowns:

$$\mathbf{A} \mathbf{x} = \mathbf{b} \implies \begin{bmatrix} a_1 & b_1 \\ a_2 & b_2 \\ a_3 & b_3 \end{bmatrix} \begin{bmatrix} x \\ y \end{bmatrix} = \begin{bmatrix} c_1 \\ c_2 \\ c_3 \end{bmatrix}$$

```text
       CASE 1: Concurrent                CASE 2: Pairwise Intersections
      (Single Shared Point)                    (Forms a Triangle)
               \   /                                   /\
                \ /                                   /  \
      ───────────X───────────                       /      \
                / \                                ──────────
               /   \                             3 distinct vertices
```

#### Analyzing System Consistency

Because the number of equations ($m = 3$) exceeds the dimension of the variables ($n = 2$), a single common solution $(x, y)$ exists if and only if all three lines are **concurrent**.

To systematically determine the geometric scenario:
1. **Solve a Non-Parallel Pair**: Select two lines (e.g., $L_1$ and $L_2$) whose determinant $D_{12} \neq 0$ and find their unique intersection $P(x_0, y_0)$.
2. **Substitute into the Third Equation**: Evaluate the residual error on the remaining line $L_3$:
   $$R = |a_3 x_0 + b_3 y_0 - c_3|$$
3. **Classify**:
   * If $R \le \epsilon$, $P$ lies on all three lines, proving concurrency.
   * If $R > \epsilon$, solve all pairwise intersections ($L_1 \cap L_2$, $L_2 \cap L_3$, $L_3 \cap L_1$). If three unique points exist and their Shoelace determinant is non-zero, they enclose a triangle.
   * If any pair yields $D = 0$, parallel or coincident configurations exist.

#### Safe Extraction Utility

```java
private double parseCoordinateField(TextField field, String fieldName) {
    String input = field.getText() != null ? field.getText().trim() : "";
    
    if (input.isEmpty()) {
        throw new IllegalArgumentException(fieldName + " is required.");
    }
    
    double value;
    try {
        value = Double.parseDouble(input);
    } catch (NumberFormatException ex) {
        throw new IllegalArgumentException(fieldName + " must contain a valid decimal number.");
    }
    
    if (!Double.isFinite(value)) {
        throw new IllegalArgumentException(fieldName + " must be a finite value (cannot be NaN/Infinity).");
    }
    
    return value;
}
```

### 5. Architectural Separation and Testability

To keep the application maintainable, UI layout, user interaction, domain entities, and numerical algorithms are decoupled into discrete packages:

```text
  src/main/java/
  ├── application/
  │   └── GeometryApp.java          # JavaFX lifecycle & Stage bootstrap
  ├── controller/
  │   └── GeometryController.java   # Event listeners, UI updates, field parsing
  ├── model/
  │   ├── Point.java                # Immutable record: (x, y)
  │   ├── Line.java                 # Immutable record: (a, b, c)
  │   └── GeometryResult.java       # Sealed types for calculation outputs
  └── service/
      └── GeometryService.java      # Pure computational algorithms (Shoelace, Cramer)
```

#### Advantages of Decoupling
* **Headless Unit Testing**: The core geometric algorithms in `GeometryService` have zero dependencies on JavaFX classes, allowing standard JUnit tests to execute in milliseconds without launching the JavaFX platform thread.
* **Separation of Concerns**: The controller focuses solely on gathering input and rendering labels, delegating all domain logic to the service.

## Discussion

1. **Standard Form vs. Slope-Intercept Form in Graphics**:
   * While $y = mx + c$ is frequently taught in introductory algebra, it suffers from a major computational flaw: vertical lines require an infinite slope ($m = \infty$), which triggers arithmetic errors in software. In contrast, the standard form $ax + by = c$ gracefully accommodates vertical lines ($b = 0$) and horizontal lines ($a = 0$) with uniform code paths.
2. **Tolerance-Based Geometry vs. Exact Arithmetic**:
   * Floating-point coordinates inevitably incur precision loss due to rounding in binary representation. Relying on strict equality (`== 0.0`) can cause parallel lines to register as intersecting at extreme distances or collinear points to register as tiny triangles. Adopting an explicit tolerance ($\epsilon$) is crucial for production-grade geometric software.
3. **Overdetermined Systems in the Real World**:
   * In practical surveying, robotics, and computer vision, lines derived from sensor measurements rarely intersect at an exact single point due to noise. When lines fail to meet concurrently, engineers often apply the **Moore-Penrose Pseudoinverse** or least-squares regression to compute an optimal compromise point that minimizes the sum of squared perpendicular distances.

## Key Takeaways

* **Collinearity Criterion**: Three points form a legitimate triangle if and only if their signed area determinant is non-zero ($|D| > \epsilon$); the sign also identifies clockwise versus counterclockwise vertex orientation.
* **Standard Form Benefits**: The line equation $ax + by = c$ models all 2D straight lines without encountering vertical slope singularities.
* **Cramer's Determinants**: The primary determinant $D$ reveals if lines intersect uniquely ($D \neq 0$), while auxiliary determinants $D_x$ and $D_y$ differentiate between parallel and coincident lines when $D = 0$.
* **Overdetermined Systems**: Three lines produce a $3 \times 2$ system that is generally overdetermined; solutions may yield a single concurrent vertex, a triangle of pairwise vertices, or parallel separations.
* **Input Hygiene**: User input parsing must rigorously check for empty inputs, syntax errors, infinities, and degenerate linear configurations ($a = b = 0$) prior to mathematical processing.
* **Architectural Decoupling**: Separating mathematical geometry services from the JavaFX UI controller enables clean, fast, and automated unit testing.
